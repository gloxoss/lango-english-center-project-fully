SchoolOS — Release Integration

Branches, Worktrees, Merges and Conflicts

How we took the work of many AI agents, each on its own branch, joined it into one version of SchoolOS, fixed every place where two agents had changed the same lines, checked it, and made it ready to deploy. Written as a lesson, using the exact commands and conflicts from our session.

Part A
The Big Picture
A.1What we actually did

Imagine eight builders renovating one house at the same time. One rewires the kitchen, one repaints the bedroom, one replaces the stairs. If they all worked on the same walls with no plan, they would paint over each other's wiring. So each builder worked on their own copy of the plans, and at the end someone had to combine all the copies into one final plan, deciding what to do wherever two builders touched the same wall.

That is exactly what happened with SchoolOS. Many agents (claude, codex, gemini, opencode, antigravity) each worked on a branch: a separate line of history. By the end of the day we had:

  • ~600 uncommitted changes sitting in the main folder (work saved on disk but never recorded in git).
  • 26 audit branches (audit/agent-a/..., audit/agent-c/...), each fixing one module: finance, HR, teacher portal, settings, and so on.
  • 1 dashboard branch (enhancement/agent-a/ENH-ADMIN-DASH-01) built on top of a 543-file "snapshot" of other people's unfinished work.
  • 1 huge attendance branch (IMPL-ATTENDANCE-REFORM-01-integrated, 86 commits) whose database migrations reused numbers already taken on main.

Our job was to produce one version containing all of it, that still compiles, still passes 3,532 tests, and can be deployed. The whole operation took five moves:

  1. Checkpoint: commit the uncommitted work so nothing can be lost.
  2. Worktree: open a second, separate folder to do the merging in, so your running app is never disturbed.
  3. Merge one branch at a time, smallest first, fixing each conflict as it appears.
  4. Gates: typecheck, full test suite, security and UI checks.
  5. Fast-forward the real branch to the finished result, then deploy.
Why this order matters: every step is reversible until the last one. If a merge had gone badly, we could have deleted the worktree and the main folder would never have known. Safety first, speed second.
A.2The tree of branches

Git history is a tree (more precisely a graph). Each dot is a commit; each commit points back to its parent. A branch is just a label stuck on one dot. Here is a simplified picture of our situation before merging:

o---o---o audit/agent-a/AUD-FINANCE-01 / f42c2bc4 (S-11, S-12, S-14 fixes)---o---o audit/agent-b/AUD-TEACHER-01 \ o---o audit/agent-d/AUD-SETTINGS-01 ... (26 of these) ...---17945212---6e13e293 student-directory-hardening (our checkpoint) \ (3d78a159 snapshot)---o---o---o---o---o ENH-ADMIN-DASH-01 34c5ce10---o---o---...(86 commits)---o IMPL-ATTENDANCE-REFORM-01-integrated

After merging, all of those lines join back into one line, with a merge commit at each join point:

6e13e293---M1---M2---M3--- ... ---M26---D1..D5---MA---fa94197d / / / / | / (each audit branch) (last audit) | (attendance) (dashboard commits copied in)

M1..M26 are merge commits for the 26 audit branches, D1..D5 are the five dashboard commits we copied (cherry-picked), MA is the attendance merge, and fa94197d is the last fix-up commit after the checks.

Part B
Core Concepts
B.1Commits and branches
The Mental Model

A commit is a saved snapshot of the whole project plus a note ("message") and a pointer to the commit before it. It has an ID like 6e13e293 (a short form of a long fingerprint). Once made, it never changes.

A branch is not a copy of your files. It is only a movable name tag pointing to one commit. When you make a new commit "on" a branch, git moves the tag forward to the new commit. That is why branches are cheap: creating one is just writing a 40-character ID into a small file.

Files you edited but did not commit are not in any branch yet. They only exist on disk. That is why our first move was a checkpoint commit: 620 files of agent work were at risk as long as they only lived on disk.

What we ran
git add -u # stage every change to files git already tracks git add lango-app/src lango-app/migrations lango-app/scripts ... # stage chosen NEW files git status --short | grep '^??' # check what is still untracked (left out on purpose) git commit -m "chore: checkpoint all agents' ... work before integration"

Line by line: git add -u adds modifications and deletions of already-known files. The second git add names only the folders we wanted, so junk like cookies.txt, a .rar archive, zip files and scratch scripts stayed out. git status --short prints one line per file; ?? means "untracked". We read that list before committing so no secret or junk slipped in.

Gotcha we hit: one of the add commands used a fancy exclude pattern and silently staged nothing. We noticed only because we counted the staged files (529, then 620 after retrying). Always count or list what you staged before committing.
B.2Worktrees: a second desk for the same project
The Mental Model

Normally one git project = one folder = one branch checked out at a time. A worktree lets the same project have several folders at once, each on a different branch, all sharing the same history. Think of it as a second desk in another room: same filing cabinet (history), different papers on the desk.

We needed this because your main folder was busy: your dev server on port 3111 was running from it, and other agents had their own worktrees too (we counted about 30 in git worktree list). Merging in the main folder would have changed files under a running app mid-way, and a half-finished merge would have left the app broken.

What we ran
git worktree add -b integration/all-2026-09-25 .worktrees/INTEGRATE-ALL HEAD cmd /c mklink /J .worktrees\INTEGRATE-ALL\lango-app\node_modules lango-app\node_modules cp lango-app/.env .worktrees/INTEGRATE-ALL/lango-app/.env
  • git worktree add creates the folder .worktrees/INTEGRATE-ALL, creates the new branch integration/all-2026-09-25 (-b) and starts it at HEAD (our checkpoint).
  • mklink /J creates a Windows junction (a folder shortcut) so the worktree reuses the existing 1.5 GB of node_modules instead of reinstalling. Good enough for typecheck and tests.
  • .env is never in git, so a fresh worktree does not have it. We copied it so tests find the database.
Limit of the junction trick: Next.js Turbopack refuses to run a dev server when node_modules is a link pointing outside the project. That is exactly the wall Agent B hit earlier. Junctions are fine for tsc and vitest; to run the app from a worktree, do a real npm install there. It is also why we deployed from the main folder, not the worktree.
B.3Merge and the merge-base
The Mental Model

To merge branch B into your branch A, git does a three-way merge. It finds the merge-base: the last commit both branches share (their common ancestor). Then, for each file, it compares three versions:

  • base: how the file looked at the common ancestor;
  • ours: how it looks now on our branch (A);
  • theirs: how it looks on the branch coming in (B).

The rule is simple. If only one side changed a region, git takes that side automatically. If both sides changed the same lines differently, git cannot know who is right. That is a conflict, and a human (or careful agent) must decide.

region changed by... result ------------------------------------------ nobody keep base only ours take ours (automatic) only theirs take theirs (automatic) both, identically take it (automatic) both, differently CONFLICT (you decide)
What we ran
git merge-base --is-ancestor "$b" HEAD && echo "already merged" git merge --no-ff -m "merge: $b into integration" "$b"

--is-ancestor asks "is branch b already inside our history?". If yes, skip it. --no-ff ("no fast-forward") forces git to create a merge commit even when it could just slide the label forward. That gives every branch its own visible join point, so later you can see exactly what came from where, or undo one branch by reverting its merge commit.

We merged smallest first. Small branches rarely conflict and they settle the shared ground early; by the time the big finance and attendance branches arrived, most overlapping changes were already in place.

B.4Conflicts: reading the markers
The Mental Model

When git hits a conflict, it stops, writes both versions into the file between markers, and waits. The file will not compile until you remove the markers. Here is the very first real conflict we got, in the timetable screen:

<<<<<<< HEAD onClick={printTimetable} disabled={loading || slots.length === 0} ======= onClick={() => window.print()} >>>>>>> agentb/academics-audit
  • Between <<<<<<< HEAD and ======= is ours: the version on our integration branch (main's newer code, which prints a real PDF and disables the button when there is nothing to print).
  • Between ======= and >>>>>>> branch-name is theirs: the version from the branch coming in (an older window.print()).

Resolving means editing the file into the correct final code and deleting the three marker lines. You have four choices per conflict block (called a hunk):

Ours

Keep our side. We did this for the print button: main's version was newer and better.

Theirs

Keep the incoming side. We did this for the website hero title, where the branch's inline white colour was more reliable.

Both

Keep both, in order. We did this for import lines and for the agent-hub changelog, where each side only added entries.

Hand-merge

Write a new version combining ideas from both. We did this in the header and sidebar.

Finishing a conflicted merge
git diff --name-only --diff-filter=U # list files still in conflict (U = unmerged) # ...edit each file, remove all markers... git add path/to/file.tsx # "I resolved this one" git commit --no-edit # finish the merge with its prepared message
Golden rule: never choose a side blindly. Before resolving, ask "what did each side mean to do?". Twice in our session both sides were the same fix written two ways (dashboard finance totals, website title colour). Choosing blindly there is harmless. But in settings, one side was translation work and the other a whole feature rewrite; a blind "ours" would have thrown away the feature.
B.5Cherry-pick: copying chosen commits
The Mental Model

Merging brings in a branch's entire history. Sometimes you do not want that. The dashboard branch was built on top of 3d78a159, a 543-file snapshot of other agents' unfinished work. Merging the whole branch would have dragged those stale copies back in and overwritten newer code.

Cherry-pick copies only the changes of specific commits onto your branch, as new commits. It is like photocopying five pages out of a book instead of taking the whole book.

git log --oneline --reverse 3d78a159..enhancement/agent-a/ENH-ADMIN-DASH-01 # cdf0dcc9 feat: admin shell + director dashboard # 4c9632a8 docs: final report # 8115a73f fix: announcements respect their audience # f1db14e8 docs: review follow-ups # e204088e fix: duplicated count on KPI card git cherry-pick -x cdf0dcc9 # conflicted in 3 files, we resolved them git cherry-pick --continue git cherry-pick -x 4c9632a8 8115a73f f1db14e8 e204088e # all clean

A..B means "commits reachable from B but not from A", so 3d78a159..branch lists exactly the agent's own work above the snapshot. -x appends "(cherry picked from commit ...)" to the message so the origin stays traceable. Conflicts during a cherry-pick look and resolve exactly like merge conflicts; you finish with git cherry-pick --continue.

Side effect to know: cherry-picked commits get new IDs. That is why, afterwards, git still reported ENH-ADMIN-DASH-01 as "7 commits not merged". The content is in; the original IDs are not. Do not panic when you see that.
B.6Fast-forward: moving the label

When all the merging was done on integration/all-2026-09-25, the real branch student-directory-hardening was still pointing at the checkpoint. The integration branch was simply ahead of it on the same line. In that situation, git does not need to merge anything: it just moves the label forward. That is a fast-forward.

git merge --ff-only integration/all-2026-09-25

--ff-only means "only move the label; if a real merge would be needed, refuse". It is the safest way to update a shared branch, because it can never invent a merge commit or rewrite anything.

The snag we hit

The fast-forward refused: "untracked working tree files would be overwritten". Agents had left untracked copies of audit reports in your main folder at the same paths the branches were bringing in as tracked files. Git will never silently overwrite a file it does not know about. We did not delete them. We moved all 282 untracked artifact files into a backup folder, fast-forwarded, then moved back the 199 that no longer collided. The other 83 now live in git, and your local copies stay in schoolos-untracked-backup-2026-09-25.

Part C
Implementation & Practice
C.1Every conflict we fixed, and why

This is the heart of the lesson: the decision behind each conflict. Notice that most were not real disagreements.

1. Timetable print button (academics)

Ours. Main had the newer PDF print with a disabled state; the branch had the older window.print(). Later, the typecheck caught a side effect: the branch had renamed the locale prop to _locale (the underscore means "unused"), but main's print code still used locale. We renamed it back. Lesson: a conflict you resolved can still break code outside the conflict block. Always typecheck after resolving.

2. Dashboard finance totals

Ours. Both sides fixed the same bug (collection rate above 100%) in two ways. Before choosing, we searched the file to make sure nothing else referenced the discarded side's variable (openByMonthMap).

3. tsconfig.json (many times)

Ours, automatically. Every agent added its private build folder (.next-aud-live, .next-agentb…) to tsconfig.json. Pure noise. After seeing it twice we taught the merge loop: "if the only conflicted file is tsconfig.json, keep ours and continue". Automate only what you have understood by hand first.

4. Teacher portal and students list

Ours. One comment wording and one line-wrapping difference. Main's comment was more complete (it mentioned receptionists too).

5. Settings (8 files, the hard one)

We did not decide by looking at the markers. We compared how much each side changed since the merge-base (git diff --shortstat base HEAD -- file versus base branch -- file). Main had ~100–170 lines of translation work; the branch had up to 1,300 lines of feature rewrite that also claimed to include the same translation (finding S-7). We read main's substance (git diff -w, ignoring whitespace) to confirm. Decision: theirs for the four rewritten screens (git show :3:path > path writes the incoming version), hand-merge for the settings hub so main's S-26 fix survived. That produced duplicated imports, which we cleaned by hand.

git show :1:path # the base version git show :2:path # ours git show :3:path # theirs
6. Website title colour

Theirs. Same fix both sides; the branch's inline style={{color:'#fff'}} beats any global CSS, so it is the more reliable one.

7. Finance (13 files)

A written rule, applied per hunk: import-only hunks → keep both (deduplicated); hunks where the branch introduced formatMoney (consistent money display, the point of the finance audit) → theirs; layout hunks where main used the correct asChild link button → ours. The shared money formatter itself → ours, because the rest of main was built on it.

8. Header and sidebar (dashboard cherry-pick)

Hand-merge. Main had an isMounted guard (prevents a flicker/hydration mismatch on first load); the dashboard added a "mark announcements read" action, the school name, and moved the profile menu. Keeping both sides created duplicated declarations of userName and roleLabel, which we deleted by hand, and the typecheck confirmed zero errors.

C.2The migration number clash

This was the most dangerous part, because git did not report it as a conflict. Main had migrations 0158_refund_cap..., 0159_salary_payment_retry, 0161_timetable_no_overlap. The attendance branch had 0158_attendance_session_occurrence, 0159_attendance_flag_lifecycle, 0161_class_session_exceptions. Different file names, so git happily kept both. Two files numbered 0158 is a bug git cannot see.

Drizzle (our database migration tool) runs migrations listed in migrations/meta/_journal.json, and decides what is new by each entry's when timestamp: anything later than the last applied migration runs. So we:

  1. renamed the three attendance files to 0162, 0163, 0164 with git mv (so git records a rename, not a delete plus add);
  2. rebuilt the journal from main's version and appended three entries with their original timestamps, which were all later than main's last one;
  3. verified: 166 entries, indexes in order, every .sql file has a journal entry and vice versa;
  4. applied them to the test database, then the dev database: migrations applied successfully, 166 recorded.
Lesson: "git merged it cleanly" does not mean "it is correct". Numbered files, generated files and lock files need their own check after every merge.
C.3Gates after merging

A merge can be textually clean and still broken. So after merging, we ran the gates, in order from fastest to slowest:

npx tsc --noEmit -p . # types: 0 errors npx drizzle-kit migrate # on schoolos_audit (test DB) npx vitest run --project unit # 3,528 / 3,532 passed at first npm run check:isolation # tenant-isolation rules: pass node scripts/check-missing-i18n-keys.mjs # missing translations: 0 npx tsx scripts/check-ui-reality.ts # dead buttons / unlinked pages ratchet

The 4 failing tests were all stale tests, not bugs. A settings fix made "delete a user of another school" return 404 instead of 200, which is stricter, and the old test still expected 200. And a finance test was pinned to the exact text of code that the dashboard version had replaced with a different, still-correct formula. We rewrote those tests to check the rule (invoice-based rate; one tenant filter per query) instead of an exact line of code. The UI ratchet caught two real gaps from the attendance work: the new "Suivi & alertes" page had no menu entry (we added one), and a deliberately disabled button looked "dead" (we raised the baseline by one, with a written reason).

How to tell a stale test from a real bug: read what the test protects. If the protected property still holds (the other school's user still exists; the rate is still invoice-based) and only the shape changed, update the test. If the property itself broke, fix the code.
C.4The recipe, step by step

This is the minimal version you can reuse any time. Comments explain each line.

# 0. Where am I, and what is not saved? git status --short git worktree list # 1. Save everything real (review the list first!) git add -u git add <the new folders you want> git commit -m "chore: checkpoint before integration" # 2. Separate desk for merging git worktree add -b integration/today .worktrees/INTEGRATE HEAD cd .worktrees/INTEGRATE # 3. Which branches have work I don't have? (smallest first) for b in $(git for-each-ref --format='%(refname:short)' refs/heads); do echo "$(git rev-list --count HEAD..$b) $b" done | sort -n # 4. Merge one at a time git merge --no-ff -m "merge: <branch>" <branch> # conflict? -> git diff --name-only --diff-filter=U # -> understand each hunk, edit, remove markers # -> git add <file> ; git commit --no-edit # typecheck after each hard one: npx tsc --noEmit # 5. Only want some commits of a branch? git cherry-pick -x <commit> ... # 6. Gates: types, migrations on the TEST db, full tests, checks # 7. Move the real branch forward (never rewrites anything) cd ../.. git merge --ff-only integration/today
C.5Best practices
Commit early

Uncommitted work belongs to no branch and can be lost by one wrong command. Checkpoint before any big operation.

Merge in a worktree

Your running app and your main folder stay untouched until the result is proven.

One branch at a time

Small steps make every conflict explainable. Smallest branches first.

Understand, then choose

Ask what each side meant. Compare sizes with --shortstat, substance with diff -w.

Typecheck after resolving

Resolved blocks can break code elsewhere (the _locale rename).

Check what git can't see

Migration numbers, journals, generated files, baselines.

Never overwrite unknown files

Move them to a backup folder instead of deleting; restore what doesn't collide.

Keep agents on fresh bases

Branches built on snapshots of unfinished work cause the worst conflicts. Start each agent from a real commit.

C.6When things go wrong

"I'm in the middle of a merge and it's a mess." git merge --abort returns to exactly how things were before the merge started. For cherry-pick: git cherry-pick --abort. Nothing is lost.

"index.lock: File exists". Another git process (often the editor's git panel) was running at the same moment. Wait a second and retry; delete the lock only if you are sure no git process is running.

"untracked working tree files would be overwritten". Move those files aside (do not delete), retry, then compare and restore.

"A branch still shows as unmerged but I merged it". Probably you cherry-picked it (new commit IDs) or merged a newer copy of it. Compare content: git diff HEAD branch -- path.

"Everything merged but the app breaks". That is what gates are for. Run types, then migrations on the test database, then the full test suite, before touching the real branch or the server.

The commands we avoided on purpose: git stash, git reset --hard, git checkout -- file, git clean. In a folder shared by many agents they can silently destroy someone else's work. Everything we did could be undone.
