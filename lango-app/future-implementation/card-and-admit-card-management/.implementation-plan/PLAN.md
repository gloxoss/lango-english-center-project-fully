# Card & Admit Card Management — Implementation Plan

> Read `future-implementation/_shared/APP-CONTEXT-AND-UI-SYSTEM.md` FIRST. Read the source spec `CARD-AND-ADMIT-CARD-MANAGEMENT.md` and `REFERENCE-REPOSITORIES.md` in this same folder — they already contain thorough, accurate product logic (page architecture, lifecycle rules, permissions, privacy requirements) and this plan does not repeat them. This plan's job is narrower: correct/confirm the source spec against the REAL current codebase, decide the one big open architecture question (the shared PDF engine), and give an executable build order.

## 1. What's already real vs. what the source spec assumes

The source spec's own "Where SchoolOS is today" section is accurate and was verified again for this plan:

- **Confirmed dead**: `certificates`/`courses` tables — zero routes reference either, `Schema.ts` has an explicit header comment (`Schema.ts:98-103`) marking the whole `academicYears/academicTerms/programs/courses/studentGroups` chain as a dead LMS/course-platform remnant. Do not build on it, per the source spec's own instruction.
- **Confirmed real and reusable**: `user` table already has `employeeId` (unique), `hireDate`, `qualification`, `documents` jsonb, `branchId`, `matricule` (unique), `classSectionId`, `photoUrl` (`Schema.ts:476-570`). `branches` has `name`/`code`/`address`/`phone`/`email`/`city` (`Schema.ts:76-96`) — **no logo field on branches**, only `tenants.logoUrl`/`faviconUrl` (`Schema.ts:60-74`).
- **Confirmed real, copy this exact pattern for template asset uploads**: `src/app/api/settings/logo/route.ts` — `GET` serves via `readUploadedFile`, `POST` validates jpeg/png ≤2MB via `saveUploadedFile`/`src/libs/api/uploads.ts`, updates `tenants.logoUrl`. Use the same helper (or `src/libs/api/blob-store.ts` if template assets need versioning — see §3) for template background images/fonts/logos.
- **Confirmed real, wrong pattern to copy for actual card/certificate PDF output**: `jspdf`/`html2canvas` are installed but have **zero real usages anywhere in `src/`** — the source spec's claim of an "existing jsPDF/html2canvas invoice pattern" does not exist in the current codebase. The two real print/PDF patterns that exist are (a) `pdfkit` server-side generation (`src/addons/advanced-reporting/services/exporters/pdf-exporter.ts`) and (b) a `window.open()` popup + `window.print()` pattern for a single simple badge (`src/features/attendance/ui/badge-management-view.tsx:140-172`, real, working, in production for attendance QR badges today). Neither is adequate for this addon's actual requirements (vector text/QR, exact mm sizing, duplex, sheet imposition, crop marks) — this confirms the source spec's own conclusion that `pdfme` is needed, not an incremental improvement on `jspdf`.
- **Confirmed real and directly reusable for admit cards**: the exam-master system built this session (`src/features/assessment/models/assessment-schema.ts`) already has `examTerms` (session/name/code/dates/status lifecycle), `examHalls` (branch/name/code/capacity), `examSeats` (**`examTermId` + `examHallId` + `studentId` + `seatNumber` + `deskLabel` + `candidateNumber`, unique per `(examTermId, studentId)`** — this is functionally identical to the source spec's proposed `examCandidates` table), and `examSchedules` (term + assessment + hall + start/end time, with real conflict detection via `ExamMasterService.createExamSchedule`). **Decision: do not build the source spec's proposed `examEvents`/`examEventSubjects`/`examCandidates` tables.** Reuse `examTerms` as `examEvents`, `examSchedules` as `examEventSubjects`, `examSeats` as `examCandidates` — they already have candidate numbers, seat/room/hall assignment, and a real service layer (`ExamMasterService`) with tenant-scoped, cross-tenant-hardened routes (`/api/academics/exam-terms`, `/api/academics/exam-halls`, `/api/academics/exam-schedules`, `.../seat-allocation`). Admit-card generation becomes a consumer of this existing data, not a new parallel domain. Verify at execution time whether `examSeats` needs one or two additional nullable columns (e.g. `accommodations`/`eligibilityStatus`) rather than a whole new table — extend, don't duplicate.

## 2. The one big architecture decision: shared `document-studio` engine

Both this addon and the future certificate-management addon depend on the same `pdfme`-based visual template designer + generation engine, per both source specs' own explicit instruction ("neutral internal library, not inside one addon importing another addon's private UI"). **This plan builds that shared foundation, since card-management is being planned first.**

- New package location: `src/libs/document-studio/` (not inside `src/features/cards/` — it must be importable by the future certificate-management feature without reaching into this addon's internals).
- Wraps `@pdfme/generator` (server-side PDF generation from a JSON template + data), `@pdfme/schemas` (built-in element types: text, image, QR, barcode, table, shape), and `@pdfme/ui` (the designer component, used client-side in the template editor). Current published version: `6.1.12` across `@pdfme/generator`/`@pdfme/ui`/`@pdfme/common`/`@pdfme/schemas` — confirm current version again at execution time, this is a fast-moving package.
- `document-studio` owns: the JSON template schema type (a thin wrapper around pdfme's own template format), a `renderPdf(templateSchema, dataRecord)` server function, a `<TemplateDesigner>` client component wrapping `@pdfme/ui`'s designer with SchoolOS's own toolbar/save/publish chrome (not pdfme's own playground UI — the source spec is explicit about this), and a field-allowlist validator (structured JSON describing which data fields a given audience/category may bind to — this directly implements both source specs' "no arbitrary SQL/JS, allowlisted field browser" requirement).
- `document-studio` does NOT own: tenant persistence, RBAC, issuance lifecycle, verification tokens, or job queues — those stay in each addon (`documentTemplates`/`documentTemplateVersions` for cards, `certificateTemplates`/`certificateTemplateVersions` for certificates later, both pointing at the same underlying JSON schema shape but as separate tenant-scoped tables, per each addon's own data-ownership boundary).
- First implementation step (matches the source spec's own "Suggested implementation order" #2 and the shared reference doc's infra-spike guidance): before any schema/CRUD work, spike `pdfme` inside this Next.js app with ONE fixed, hardcoded student card template, real Arabic + French font embedding, and confirm both the browser designer preview and a server-side batch render actually work end-to-end. This is a real, non-trivial technical risk (font embedding + RTL + browser/Node parity) — validate it in isolation first, exactly as the source spec recommends.

## 3. Storage for template assets and rendered output

Reuse `src/libs/api/blob-store.ts` (`BlobStore`, `blobKeyFor`) from the attachments-book addon rather than `src/libs/api/uploads.ts`'s simpler helper — template background images, fonts, and rendered card/PDF output all need the same "versioned, immutable, content-addressed" properties attachments-book already solved (`published template version is immutable`, `issue snapshots resolved printable data`). Do not re-invent this. `documentTemplateVersions` rows store a `storageKey` pointing into the same `BlobStore`, same as `digitalAssetVersions` does.

## 4. Schema — adopt the source spec's model with the one reuse correction from §1

Build exactly what `CARD-AND-ADMIT-CARD-MANAGEMENT.md`'s "Recommended data model" section specifies (`documentTemplates`, `documentTemplateVersions`, `issuedDocuments`, `documentGenerationJobs`, `documentGenerationItems`, `documentEvents`) as a new feature schema at `src/features/cards/models/cards-schema.ts`, following the shared reference doc's schema conventions exactly (barrel export line in `Schema.ts`, hand-written migration, no `drizzle-kit generate`). **Do not build `examEvents`/`examEventSubjects`/`examCandidates`** — reference `examTerms`/`examSchedules`/`examSeats` from `src/features/assessment/models/assessment-schema.ts` instead (cross-feature import, same pattern already established between attachments-book and the assessment feature's `resolveStudentAudienceContext`).

## 5. Permissions

New capability keys following the established `module.action` convention (`src/libs/api/permissions.ts`): `cards.templates.manage` (admin-only, taxonomy/designer), `cards.issue` (admin + authorized receptionist/exam-coordinator per the source spec's permission table — grant to `school_admin` automatically via `ALL_PERMISSIONS`, add explicit grants to `receptionist`/relevant roles in `DEFAULT_ROLE_PERMISSIONS`), `cards.revoke`. Confirm the exact role names available in this codebase's `AppRole` union before assigning (`receptionist` role existence was referenced in this session's other work — verify it still matches).

## 6. Page architecture

Use the source spec's page list verbatim (`CARD-AND-ADMIT-CARD-MANAGEMENT.md` §"Page architecture", routes `/dashboard/cards`, `/dashboard/cards/templates`, `/dashboard/cards/templates/[id]/edit`, `/dashboard/cards/students`, `/dashboard/cards/employees`, `/dashboard/cards/admit-cards`, `/dashboard/cards/issued`, `/dashboard/cards/jobs`, public `/verify/card/[token]`) — it is already well-specified and does not need re-deriving. Build every page per the shared UI system doc's conventions: single-file `'use client'` pages, real `fetch()`, KPI banner header, `Badge` variant enum exactly `success|danger|warning|info|neutral|signal`, sidebar registration under a new "Cartes & Documents" nav section gated by `cards.issue`/`cards.templates.manage`. The template designer page (`/templates/[id]/edit`) is the one page that legitimately needs a large, focused client component wrapping `@pdfme/ui` — that's the one exception to "keep pages single-file," and it should still use SchoolOS's own surrounding chrome (header, save/publish buttons, KPI-style status bar) rather than pdfme's own UI shell.

## 7. Suggested build order (adapts the source spec's order to this codebase)

1. Addon activation/entitlement check — real, working helper already exists: `requireAddon(tenantId, addonId)` in `src/libs/api/entitlements.ts` (also `hasAddon`, `listEntitlements`, `assertKnownAddon`). Register this addon's id, call `requireAddon(tenantId, 'cards')` at the top of every route alongside `requireTenant`. Don't invent a second addon-gating mechanism.
2. `document-studio` pdfme spike (§2) — prove the technical foundation before any schema work.
3. `document-studio` package proper: template schema type, `renderPdf`, `<TemplateDesigner>`, field allowlist validator.
4. Cards schema + migration (§4), Template Library + Designer pages.
5. Issued-document/token/event lifecycle + public verifier (`/verify/card/[token]`) — token hashing, rate limiting, generic invalid-token response, per the source spec's privacy/security section verbatim.
6. Student ID cards page + production print sheet (A4 imposition, mm-exact, crop marks) — this is the first real proof the whole pipeline works end-to-end.
7. Employee ID cards (reuses everything from step 6, different field set).
8. Admit cards: wire to real `examTerms`/`examSchedules`/`examSeats` per §1's reuse decision, build the selection/eligibility/preview/generate flow.
9. Async job system for batch generation (`documentGenerationJobs`/`documentGenerationItems`) — do not block one HTTP request rendering hundreds of cards; check whether this codebase has any existing background-job pattern before inventing one (search for existing job/queue infrastructure at execution time — if none exists, the simplest correct approach is a job row + a route that processes N items per invocation, polled/triggered rather than a full queue system, matching this app's no-queue infra reality per the shared reference doc's scope-sizing discipline).
10. QR/attendance integration (verification token as an attendance-QR credential source) — coordinate with the attendance-qr-enhancement plan's `identityBadgeCredentials` system; these are related but distinct per both specs, confirm the exact integration point at execution time rather than assuming.

## 8. Acceptance checklist (live-verify, no self-reporting)

- [ ] `pdfme` spike renders a real card with correct Arabic RTL + French text, both in-browser preview and server batch output, before any further schema work is trusted.
- [ ] Publishing a template version makes it immutable — attempt an edit/delete on a published, in-use version and confirm it's rejected.
- [ ] Issue a real student card, confirm the QR verification token is opaque (not the student's real DB id/matricule) and hashed at rest; confirm `/verify/card/[token]` returns a generic result for both a real revoked card and a nonexistent token (no enumeration difference).
- [ ] Bulk-issue a batch, kill/retry mid-batch (or simulate), confirm no duplicate active card is created for any single student (job-item uniqueness).
- [ ] Generate a real admit card from real `examTerms`/`examSeats` data, confirm candidate number/room/seat match the real exam-master records exactly.
- [ ] Cross-tenant sweep on every new route (template CRUD, issue, revoke, verify) — same rigor as every other feature built this session.
- [ ] Disabling the addon entitlement blocks new template/issue actions but existing issued cards still verify.
