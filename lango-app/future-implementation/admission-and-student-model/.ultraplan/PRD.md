# Admission Flow & Student Model Enhancement - Product Requirements

> Generated by UltraPlan | 2026-08-06
> This document describes what we're building in plain English.
> For the technical implementation plan, see PLAN.md.

## What We're Building

We're fixing and completing the "add a new student" process in SchoolOS. Right now, when a school admin enrolls a new student, the form collects only basic information, one entire step (uploading the student's photo and documents) doesn't actually save anything, and the new student has no way to log into the system once enrolled. We're closing those gaps: adding the extra fields a real school needs (gender, nationality, mother tongue, and a few others), making document upload actually work, properly linking parents/guardians instead of just typing their name as text, and generating real login access the moment a student is approved.

## The Problem

The admission wizard looks complete but has three real gaps hiding behind a polished UI. First, the "Documents & consentements" step lets an admin pick files to upload, but nothing is ever saved — those files vanish. Second, when an admin types a parent's name and phone number, that information goes nowhere useful; it's just text sitting on the student's record, disconnected from the real parent/guardian system used everywhere else in the app. Third, once a student is approved and enrolled, they have no account — no way to log in — until someone handles that separately, through some other process nobody has actually built yet.

## Who It's For

**School Admins** (primary): The staff members who run the admission wizard when a new student joins. They fill out the multi-step form, upload documents, and click "Approve" to officially enroll a student. They need the form to actually save what they type and upload, and they need approving a student to be a complete action — not one that leaves manual follow-up work.

**New Students & Their Guardians** (indirect, but the real payoff): Once approved, a student's guardian should be able to actually get into the system — either through a link that lets them set their own password, or a temporary password the school shares with them — instead of being enrolled but locked out.

## What It Does

### Must Have (Wave 1 — real bug fixes + new fields)
- **Working document upload**: Photos, birth certificates, previous school certificates, and guardian ID copies uploaded during admission are actually saved, not lost.
- **New student fields**: Gender, Academic Year, Nationality, Mother Tongue, City, and (optional) Blood Group are collected during admission and saved on the student's record.
- **Profile picture from admission**: The photo uploaded during admission becomes the student's profile picture automatically — no separate step needed later.
- **Correct student ID numbers**: Fixes a bug where approved students sometimes get a randomly generated ID number instead of the real, properly sequenced one the rest of the school already uses.

### Must Have (Wave 2 — bigger behavior changes)
- **Real parent/guardian linking**: Instead of just typing a parent's name as text, the admin searches for an existing guardian first (so siblings don't create duplicate parent records) and only creates a new guardian record if no match is found. This properly connects the student to the real parent-contact system used elsewhere in the school.
- **Real login access on approval**: The moment a student is approved, they (and/or their guardian) get real access to the system — either an invite link to set their own password, or a temporary password the school can share, depending on which method the school prefers (chosen once in Settings).

### Explicitly Not Included
- Caste, Category, Religion, "State" (US/India-specific fields with no meaning in this school's context — see "What It Does NOT Do")
- Transport/Hostel sections on the admission form
- A second "Roll Number" system separate from the existing student ID

## How It Should Feel

This extends the existing 4-step admission wizard — no new screens, no new navigation pattern, no visual redesign. The new fields slot into the existing "Informations élève" step using the same input style already there. The guardian search feels like typing a name and seeing real matches appear, the same way searching already works elsewhere in the app. Document upload should feel instant — pick a file, see a checkmark, move on — with no separate "save" button. Nothing about this should feel like a new feature bolted on; it should feel like the admission wizard finally does what it always looked like it did.

## What It Connects To

This connects to systems that already exist in SchoolOS: the real parent/guardian contact list, the school's existing file storage for photos and documents, the login system every other user in the app already uses, and the sequential ID-number system the rest of the school already relies on. It also uses the school's existing "simulated text message" system to deliver invite links — this school doesn't have a real text-message service connected yet, so message delivery is logged and shown in the app rather than actually sent, exactly like every other "send a notification" feature already in this product.

## What It Does NOT Do

- Does not add Caste, Category, Religion, "State", Transport, Hostel, or a second Roll Number system — all explicitly excluded because they don't fit this school's real context (see the source planning document's detailed reasoning).
- Does not go back and fix existing, already-enrolled student records — this only applies to new admissions going forward.
- Does not connect to a real SMS or email delivery service — invite links stay in the same "simulated, logged, shown in-app" system this product already uses everywhere else.
- Does not change anything about how classes, grades, or attendance work — this is scoped entirely to the admission process and the student record it creates.

## How We'll Know It Works

- An admin can upload a document during admission, and it's still there — visible, downloadable — after the student is approved.
- A newly approved student has a real, correctly formatted ID number every time, with zero random or duplicate IDs.
- Searching for an existing guardian during admission finds a real match if one exists, and creating a "new" guardian for someone who's already in the system becomes the exception, not the norm.
- A guardian of a newly approved student can actually get into the system using whichever access method the school has chosen, without anyone needing a manual workaround.

## Business Model

Not applicable — this is an internal operations feature for schools already using SchoolOS, not a separately monetized product or feature.

## Risks & Concerns

1. **Document upload during admission needs a small new table.** The obvious approach (reuse the existing student-document storage) doesn't work because there's no student record yet at that point in the wizard — only an "applicant" record. We're adding a small parallel table just for the admission wizard's use, then copying the files over once the student is actually approved. This is a real, deliberate design decision, not a shortcut — see RESEARCH.md.
2. **Login-access generation is genuinely new territory for this app.** Nothing like it has been built here before, so the exact technical approach (how the login system creates an account programmatically) needs to be verified carefully during implementation, not just assumed to work.
3. **Guardian search-and-link changes admin behavior**, not just the screen — admins are used to just typing a name; now they'll be asked to search first. This is the right fix for data quality, but it's a real workflow change worth a heads-up to whoever trains staff on the admission process.
