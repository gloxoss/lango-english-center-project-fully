# Alumni Portal - Technical Plan

> Generated by UltraPlan | 2026-08-06
> This document contains the technical implementation plan.
> For plain-English product requirements, see PRD.md.

## Architecture Overview
Pure extension of the existing SchoolOS/Lango stack: Next.js App Router, Drizzle ORM, PostgreSQL, Better Auth, multi-tenant. One combined migration (`0061_alumni_portal.sql`) adds a new `alumni` role value plus 6 new tables. A genuinely new route group `(alumni-portal)` gives alumni their own self-service shell, separate from the staff `(dashboard)` shell. Every new route follows the established convention (`requireRequestContext` → `requireTenant` → `requireCapability` → Zod `.strict()` → tenant-scoped query → `recordAudit()` → `apiErrorResponse()`), except the one deliberately public, no-login document-verification endpoint, which instead reuses this app's existing rate-limiting/honeypot pattern.

## Tech Stack
No new stack. Reuses: Better Auth credential issuance (admission-approval pattern), `smsMessages` (log-only notifications), `src/libs/api/uploads.ts` (tenant-namespaced file storage), `namingSeries` + `pg_advisory_xact_lock` (verification-code generation), the existing public-endpoint rate-limiter.

## Section Overview
1. **Schema & Role Foundation** — migration 0061 + Schema.ts + the 3 non-DB role touch points (`APP_ROLES`, `DEFAULT_ROLE_PERMISSIONS`, `ROLE_TO_UI`/`ROLE_TO_DB`) + the advisory-lock-safe verification-code generator, applied and Docker-verified.
2. **Graduation Transition** — the first-ever post-creation role change in this codebase: disable old student credentials, flip role, issue new real alumni credentials (reusing the admission-approval pattern exactly), plus the re-admission reversal.
3. **Alumni Portal Shell & Announcements** — a genuinely new, separate self-service route group with real auth guarding, replacing the fully fake existing `alumni-portal-view.tsx`; real profile-completeness home page; real announcements with SMS notification.
4. **Records & Document Verification** — staff issue real documents with real unique verification codes; alumni download their own; a real public no-login page confirms genuineness without exposing files.
5. **Correction/Reissue/Data/Deletion Requests** — one real staff-reviewed request queue, four types, reissue correctly supersedes the old document and its verification code in one transaction.
6. **Alumni Events & RSVP** — real, self-contained events + RSVP, not blocked on the separate unbuilt event-management addon.
7. **Opt-In Directory & Safeguarding** — real per-field consent, a real shared 18+ safeguarding helper (fail-closed on unknown age) used by both this section and mentoring.
8. **Mentoring & Volunteering Listing** — real opt-in listing, no automated matching, safeguarding enforced at both write and read time.
9. **Final Verification** — full live lifecycle test, cross-tenant isolation sweep, regression check on every adjacent existing feature (student login, admissions, promotions' own separate "graduate" concept, guardian features).

## Execution Notes (cross-cutting, applies to every task)

- **Loading/error states, accessibility, responsive layout, git collision discipline**: same conventions established in the prior `dropped-features-rebuild` plan's PLAN.md apply unchanged here — reuse existing `@/components/ui/` primitives, the existing `Loader2` spinner pattern, and re-check `git status` on any existing file before editing it.
- **Fail-closed safeguarding**: anywhere age/eligibility is uncertain (missing `dateOfBirth`, edge-of-18), the correct behavior is always to exclude, never to include — this is a hard rule for sections 07 and 08, not a judgment call per task.
- **No new capability strings beyond the small, real, minimal `alumni.*` set registered once in section-01** — every alumni-facing route reuses either that set (self-scoped, no additional capability needed since alumni can only ever touch their own rows) or the existing `admissions.manage`/`admissions.view` on the staff side.
