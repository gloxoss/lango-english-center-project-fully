## Architecture Overview
Pure extension of the existing SchoolOS/Lango stack: Next.js 15 App Router, TypeScript, Drizzle ORM, PostgreSQL, Better Auth, Tailwind, multi-tenant via `tenantId`. One combined migration (`0058_dropped_features_rebuild.sql`) adds all new columns/tables across all 6 feature areas; every route follows the established convention (`requireRequestContext` → `requireTenant` → `requireCapability` → Zod `.strict()` → tenant-scoped Drizzle query → `recordAudit()` → `apiErrorResponse()`). No new capability strings are introduced — every new route reuses an existing capability (`guardians.*`, `academics.manage`, `grading.*`, `admissions.*`, `students.read`) already governing the same resource domain, confirmed sufficient during research.

## Execution Notes (cross-cutting, applies to every UI task in every section)

- **Loading states:** every fetch triggered by a new control (toggle, form submit, tab switch) must show the same loading-indicator convention already used elsewhere in this app (the `Loader2` spinner pattern, e.g. `excel-import-view.tsx`'s `importing` state) — do not invent a new pattern.
- **Network/API failures:** every new fetch must handle a failed response the same way `student-transfers-client.tsx` already does (`error`/`success` state rendered inline, never a silent failure or an unhandled promise rejection).
- **Accessibility:** every new form control (select, toggle, checkbox, date/time picker) must use this app's existing primitives under `@/components/ui/` (per this repo's own CLAUDE.md instruction) rather than raw HTML elements — those primitives already carry the app's accessibility baseline, so this is reuse, not new a11y work.
- **Responsive/mobile:** every new layout addition (KPI cards, new panels/tabs) must reuse the existing responsive class patterns already present in the file being edited (e.g. `sm:flex-row`, `grid-cols-1 sm:grid-cols-2`) rather than a fixed-width layout.
- **Git collision discipline:** every task touching an existing file must run `git status --short` on that file before editing, even files that seem certain to be new — this repo has an actively-committing concurrent session, and this exact discipline failure caused a real incident earlier this same overall effort (see `src/app/api/students/import/route.ts` in prior session history).

### Refinement Questions & Answers
- Q: Should the system block two applicants being scheduled with the same interviewer at an overlapping time? | A: No — allow it, no conflict check (low-frequency, staff-arranged, not worth mirroring the timetable's conflict logic here).
- Q: Should a homeroom-teacher assignment auto-clear when that teacher's account is deactivated? | A: No — keep showing them, staff clears it manually (matches how this app already treats other stale staff references).
- Q: Can two guardians share the same emergency-contact priority number for the same child? | A: Yes — allowed, no uniqueness enforcement (it's a sort hint, not a strict queue).
- Q: Can a question-bank item be deleted after being copied into real exams? | A: Yes — freely, since copies are fully independent rows (added a DELETE handler to section-05 task 05-02 as a result — this was a real gap, the route previously only specified GET/POST).
- Q: Should the "students per branch" transfer KPI count every student or only active ones? | A: Active only (`userStatus = 'active'`) — updated section-07 task 07-01 accordingly.
