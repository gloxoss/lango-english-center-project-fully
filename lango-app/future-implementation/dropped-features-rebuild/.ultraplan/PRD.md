# Dropped-Features Rebuild — Product Requirements

> Generated by UltraPlan | 2026-08-06
> This document describes what we're building in plain English.
> For the technical implementation plan, see PLAN.md.

## What We're Building
Earlier this session, six pages in the school system (guardian/family profiles, class management, the class schedule, the exam question bank, admission review, and student transfers) were cleaned up by removing features that looked real but weren't backed by any actual saved data — buttons that did nothing, numbers that were made up. This plan rebuilds the genuinely useful parts of what was removed, this time backed by real, saved data, with a better layout than the original fake versions had.

## The Problem
A staff member using these pages before this session could click "Create a household," set a payment card, or approve a transfer request — and nothing would actually happen, or the number shown was invented. That's worse than not having the feature at all, because it looks trustworthy. This plan replaces those dead ends with the same features working for real, using data that's already collected elsewhere in the system wherever possible, so nothing new has to be typed in twice.

## Who It's For
**School administrators and front-desk staff** are the only users of everything in this plan — the same people who already use the guardian list, class list, schedule, question bank, admission review, and transfer form today. **Teachers** get a read-only slice of one part (their own schedule, viewed by teacher instead of by class). No student- or parent-facing screens are touched by this plan.

## What It Does

### Must Have
- **Family view for guardians**: A guardian's page groups them with the other guardians of the same child (a real "household" grouping, computed from real family links — no separate household record to create/maintain). Shows which guardian is allowed to pick a child up, who to call first in an emergency, whether they've opted into email/SMS updates, and every invoice/payment across all their children in one place.
- **Class setup upgrades**: Classes get a real education level (Preschool/Primary/Middle/High), an enrollment cap, a homeroom teacher, and a home-base room — using the school's real teacher-assignment and room records.
- **Schedule by teacher or by room**: The weekly schedule can be viewed grouped by teacher or by room, not just by class, using the same real schedule data already there.
- **Reusable exam question bank**: Questions can be tagged by subject, education level, and difficulty, saved once, and reused across multiple exams — copying a question into an exam makes an independent copy, so editing it later never silently changes an exam that's already been given.
- **Admission interview & review tracking**: Each applicant can have one real interview (date, time, interviewer, location) scheduled and tracked, a real staff-only notes thread for coordinating decisions, and a simple checklist (documents received / interview done / file complete) that's actually saved.
- **Transfer activity numbers**: The student-transfer page shows a real count of transfers this month and a real headcount per branch, computed from actual transfer records — the transfer action itself was already real before this plan and isn't being changed.

### Should Have
- Application-level protection so two staff members can't accidentally both be marked as a class's homeroom teacher at the same time.

### Nice to Have (explicitly deferred, not built in this plan)
- A visual drag-and-drop schedule editor (the current simpler list view stays).
- Notifying a guardian by SMS when an interview is scheduled (stays an internal-only record for now).
- Letting each school customize its own admission checklist wording (stays a fixed list for now).

## How It Should Feel
No new visual style. Every rebuilt page keeps the exact same look the rest of the system already has — the same color palette, the same summary-cards-at-the-top layout, the same data tables and side-panel details. Someone who already knows how to use the guardian list or class list should feel nothing has changed except that the buttons now actually work and the numbers are now real.

## What It Connects To
Nothing outside the system itself. Every feature in this plan reuses data the school already has on file — family links, room records, teacher assignments, exam records, applicant files, invoice/payment history — instead of connecting to anything new. Where a message needs to be "sent" (like a future SMS reminder), it uses the same internal message log the system already uses elsewhere, which records what would be sent without needing a live text-messaging service connected.

## What It Does NOT Do
- Does not store payment card numbers anywhere — only shows the real invoice/payment history that already exists.
- Does not build a separate "household" record to create and maintain — a household is simply the guardians already linked to the same child.
- Does not add a second interview round, an approval step for transfers, or a way for each school to customize its own checklist — all confirmed not needed right now.
- Does not touch the "bulk import from spreadsheet" page's manual single-entry tab, which was intentionally dropped earlier for duplicating the real admission form, not because it couldn't be made real.
- Does not rebuild the drag-and-drop visual schedule editor.

## How We'll Know It Works
- Every number and list shown on these six pages comes from a real, saved record — nothing hardcoded, nothing invented as a fallback.
- A staff member can schedule a real interview, add a real note, tick a real checklist item, assign a real homeroom teacher and room, tag and reuse a real exam question, and see a guardian's real combined family invoice history — and all of it is still there after refreshing the page or logging back in later.
- No existing, already-working feature (guardian editing, class CRUD, the schedule builder, exam creation, admission approval, the transfer action) breaks as a side effect of this plan.
- Every new screen keeps working correctly when tested with a different school's account, never showing one school's data to another.

## Business Model
Not applicable — this is internal tooling for schools already using the system, not a separate product with its own pricing.

## Risks & Concerns
1. **Homeroom teacher double-booking**: The safeguard that stops two teachers being marked "primary" for the same class only fully works once a separate, only-partly-finished feature (school-year-scoped class setup) is in place. Until then, this plan adds a manual check in the code itself rather than relying purely on the database to catch it — a rare timing coincidence (two staff saving at the exact same second) could theoretically slip through, which is an acceptable, low-likelihood risk for an admin action like this.
2. **Reused question bank items don't update old exams**: This is intentional — once a question has been copied into an exam, editing the original bank copy later won't change exams that already used it, so past exam results stay stable and accurate.
3. **Family payment view requires pulling together records from multiple children**: For a guardian with several kids at the school, showing their combined invoice history means gathering records from each child individually behind the scenes — done correctly, this is invisible to the user, but it's more computing work than a single lookup, worth knowing about if the page ever feels slow with an unusually large family.
