## Storage & upload pipeline

**Original spec** (`REFERENCE-TOOLS-AND-REPOSITORIES.md`) recommends Uppy + tus/tusd for resumable uploads, an S3-compatible `BlobStore` (SeaweedFS self-hosted or managed), ClamAV for scanning, and optional Apache Tika for extraction.

**Resolved against this deployment's actual infra** (conflict, resolved directly per standing directive rather than via AskUserQuestion): `docker-compose.yml` today runs exactly 3 containers (`db`, `app`, `migrate`) — no object storage, no queue, no resumable-upload service. Standing up tusd + a distributed object store now would be real, ongoing operational surface this small deployment doesn't need yet, and the reference doc itself flags this exact tradeoff ("operating distributed storage is substantial... managed S3-compatible storage may be safer for a small team"; "recommended v1 is links plus bounded small files, not a home-built video streamer"). **Decision: v1 uses single-request multipart uploads** (extending the existing `saveUploadedFile` helper pattern already used for student/teacher photos) **with a capped file size per attachment type** (default 25MB), and a `BlobStore` interface with only the operations this app actually calls today (`put`, `get`, `head`, `delete`) so a real S3-compatible adapter can be dropped in later with zero business-logic changes. Uppy/tus/tusd, SeaweedFS, and true chunked resumability are documented in PRD.md Section 7 as deliberate, reasoned follow-up work, not silently dropped.

**Malware scanning is NOT deferred** — unlike storage/resumability, this is a must-have control the moment arbitrary user file uploads become downloadable by other users, and it's a small, well-bounded addition (one more Docker service), not the kind of heavy infra being deferred above.

- **Image**: official `clamav/clamav:1.4` (Cisco-Talos-maintained, ships pre-loaded virus databases) — not a random community image. TCP 3310 (clamd), persist `/var/lib/clamav` as a named volume so signatures survive restarts (avoids re-downloading on every restart).
- **Health-gating**: `depends_on: clamav: condition: service_healthy` is required — plain `depends_on` only waits for container start, not for the virus database to finish loading, which can take 1-5+ minutes on a cold volume. Healthcheck: generous `start_period` (180s) with retries, matching the community reference pattern (`mko-x/docker-clamav`'s documented `interval: 60s, retries: 3, start_period: 120s` shape, widened slightly for safety).
- **Node client**: `clamdjs` (zero-CLI-dependency, speaks the INSTREAM TCP protocol directly, `scanBuffer(buffer, timeout, chunkSize)`) — no local `clamscan`/`clamdscan` binary needed inside the `app` container, just a TCP client. `clamscan` (npm) is the more widely-known alternative and also supports pure-TCP mode if `clamdjs` proves insufficient, but `clamdjs`'s zero-dependency shape fits this codebase's existing "small, direct helper" style (`src/libs/api/uploads.ts`) better than a heavier wrapper library.
- **Pitfall avoided**: never buffer the full file in memory for scanning — write to a quarantine subpath on disk first (reusing the existing `UPLOADS_ROOT`-relative path convention), then stream that file to `clamd`'s INSTREAM. `StreamMaxLength` in `clamd.conf` defaults to ~25MB and must be raised to match (or set equal to) this addon's max upload size, or large-but-legitimate files will hit "INSTREAM: Size limit reached."
- **Not adopted**: hosted scanning APIs (AttachmentScanner, OPSWAT) — per-scan cost and sending tenant files to a third party outweigh the ops savings for this self-hosted, small-team deployment; self-hosted ClamAV matches how every other piece of this stack already runs (own Postgres, own disk volume, no external SaaS dependencies).

## Targeting / audience resolution

Directly reuses the exact pattern already proven and unit-tested this session in `isHomeworkVisibleToStudent` (`src/features/assessment/services/homework-service.ts`): a resource with no target rows is a broadcast; a resource with target rows is visible only if one matches the viewer directly (user), their section, or an offering/subject their class participates in. Extended per the addon spec with two more target kinds this codebase doesn't have a precedent for yet: `role` (e.g. "all teachers") and `school` (explicit whole-tenant broadcast, distinct from "no targets" so admins can express it deliberately rather than relying on an implicit empty-list meaning). Same "pure function the real route calls directly" testability pattern as `isHomeworkVisibleToStudent`/`doTimeRangesOverlap` established this session.

- Schema: new `src/features/attachments/models/attachments-schema.ts`, re-exported from `Schema.ts`, migration `0063`.

- No new frontend dependency — plain fetch + existing `@/components/ui/` primitives, matching every other dashboard page.
