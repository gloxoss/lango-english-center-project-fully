# Attachments Book — Product Requirements Document

> Generated by UltraPlan | 2026-08-07 | Self-answered/compressed per standing session directive ("dont ask again do the best option always") — no interactive approval loop was run; each section below reflects the best-judgment synthesis of `ATTACHMENTS-BOOK-ADDON.md`, `REFERENCE-TOOLS-AND-REPOSITORIES.md`, and `DISCOVERY.md`.

## 1. What We're Building

A school-wide resource library inside SchoolOS where teachers and admins upload learning materials once — worksheets, notes, presentations, answer keys, policy documents — and reuse them across classes instead of re-attaching the same file to every homework or announcement. Each resource can be aimed at exactly the right audience (the whole school, a role, a specific class, or a specific student), gets scanned for malware before anyone can download it, and keeps a full version history so replacing a file never breaks something that already links to it.

## 2. The Problem

Today, a teacher who wants to share a worksheet with three different classes has to attach it three separate times, with no shared history and no way to update all three copies when they find a typo. There's no school-configurable way to say "this is an answer key, staff-only" versus "this is a public policy document" — every upload looks the same to the system. And nothing scans an uploaded file before students can download it.

## 3. Who It's For

- **School admins** — configure the taxonomy (what kinds of resources exist, their size/visibility rules), see everything in the tenant, moderate, restore or permanently remove.
- **Teachers** — create and manage resources for the classes/subjects they're assigned to, and reuse resources the school has already shared.
- **Students and parents** — browse and download only what's been published and targeted to them; never see draft, unpublished, or staff-only material.

## 4. What It Does

**v1 (built now):**
- Configurable attachment types (notes, worksheet, answer key, policy, etc.) with per-type size/MIME/visibility rules.
- Upload a resource with title, description, tags, and a precise audience (school-wide, a role, a class/section, a subject, or a single user) — "all students" is always a deliberate choice, never an accidental default.
- Full lifecycle: draft → uploading → quarantined → processing → ready → published → archived, with real failure states (upload/scan/processing failure, rejected) that block download at every step, not just at upload time.
- Real malware scanning (ClamAV) before anything is ever downloadable.
- Version history — replacing a file creates a new version; nothing that already links to an old version breaks.
- Search/filter library with table and grid views.
- Resources can be linked from a homework assignment ("reuse"), the first real consumer of the reuse model.
- Full tenant isolation and audit trail on every action, matching the rest of the app.

**Documented for later (not built now — see Section 7):** rich text/metadata extraction from documents, a storage/quota operations dashboard, bulk tenant data export, true resumable chunked uploads, and swapping the local-disk storage backend for real S3-compatible object storage.

## 5. How It Should Feel

Same look and feel as the rest of the SchoolOS dashboard — the slate/blue palette, dense data tables, a KPI banner at the top of the library page, and a slide-out inspector for a resource's details. No separate visual language, no new component library. Uploading feels like a normal form: pick a file, fill in a few fields, hit publish — not a multi-step wizard, since v1 uploads are single-request and don't need one.

## 6. What It Connects To

- Existing class/section/subject/user tables, reusing the exact audience-matching approach already proven in this codebase's homework-visibility logic.
- The existing tenant-namespaced local-disk upload helper, extended (not replaced) into a small storage abstraction.
- A new ClamAV scanning service added to the Docker Compose stack.
- Homework, as the first place a resource can be linked and reused.

## 7. What It Does NOT Do

- No true resumable/chunked uploads (Uppy + tus/tusd) in v1 — files are capped at a sane size and uploaded in a single request; the original spec's resumable pipeline is documented as a future upgrade once file sizes or unreliable-network use cases actually demand it.
- No S3/SeaweedFS object storage in v1 — resources live on the same local-disk Docker volume every other upload in this app already uses, behind a storage interface that can swap in a real object-store adapter later without touching business logic.
- No Apache Tika text/metadata extraction, no full-text search inside document contents.
- No storage/quota operations dashboard, no popular/unused-asset reports, no portability export — the core library, targeting, and lifecycle are the priority; operational reporting is a follow-up phase.
- No uploaded video hosting — video content is external links only in v1 (YouTube/Vimeo/etc.), matching the reference doc's own recommendation.
- Does not touch or replace existing student documents, photos, or homework-attachment mechanisms — those keep working exactly as they do today.

## 8. How We'll Know It Works

- A teacher can upload a worksheet, target it at one class, and only students in that class see it — verified live, not just by code inspection.
- Replacing a file preserves the old version and doesn't break a homework that links to it.
- An infected test file (EICAR test string) is rejected and never becomes downloadable.
- A cross-tenant sweep (the same technique used twice already this session) finds zero ways for one tenant to read, write, or reference another tenant's resources.
- `tsc --noEmit` and the project's tenant-isolation script both pass clean after implementation.

## 9. Business Model

Not applicable — internal school-operations feature, included in the existing per-tenant product, no separate pricing or subscription tier.

## 10. Risks & Concerns

1. **Malware scanning is new infrastructure** (ClamAV as a Docker service) — first time this app has run a scanning daemon; startup/health-check timing (virus database load) needs care so uploads don't silently bypass scanning during a cold start.
2. **Audience-targeting correctness is security-sensitive** — get it wrong and a student could see a staff-only answer key. Mitigated by reusing the exact, already-battle-tested audience-matching pattern from homework, plus a live cross-tenant/cross-audience sweep before calling this done (same discipline as the two prior remediations this session).
3. **Scope discipline** — the source spec is large (6 phases); the real risk is over-building infrastructure this deployment doesn't need yet (resumable uploads, distributed object storage, extraction workers) at the expense of shipping a correct, secure core. This PRD deliberately narrows v1 to what's proportionate and documents the rest as follow-up, not as silently dropped scope.
