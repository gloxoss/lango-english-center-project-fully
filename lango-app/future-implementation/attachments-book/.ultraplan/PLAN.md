# Attachments Book — Technical Plan

> Generated by UltraPlan | 2026-08-07

## Architecture Overview

A new self-contained feature module (`src/features/attachments/`) inside the existing Next.js 15/16 / Drizzle / PostgreSQL multi-tenant SchoolOS app, following every convention already established and repeatedly proven this session (route chain, capability keys, tenant scoping, pure-function-extraction-for-testability, audit trail). Two genuinely new pieces of infrastructure are added: a `BlobStore` abstraction (local-disk adapter for v1, interface designed so a real S3-compatible adapter can be added later with zero business-logic changes) and a ClamAV malware-scanning Docker service (the one piece of infra from the source spec judged non-negotiable rather than deferrable). Everything else the source spec envisions as heavier infrastructure — resumable/tus uploads, distributed object storage, Apache Tika extraction, an operations/reporting dashboard — is deliberately scoped out of v1 as documented, reasoned follow-up work (see PRD.md Section 7 and RESEARCH.md's "Storage & upload pipeline" section for the full reasoning), matching this deployment's actual 3-container Docker Compose maturity level.

## Tech Stack

- No new frontend dependencies (plain fetch + existing `@/components/ui/` primitives, matching every other dashboard page).
- One new backend dependency: `clamdjs` (zero-CLI-dependency ClamAV TCP client).
- One new Docker service: `clamav/clamav:1.4` (official Cisco-Talos image).
- Everything else (schema, routes, auth, upload validation) extends existing in-repo code.

## Review Notes — Section 09 Live Execution Findings (2026-08-07)

All live verification was run against the real running app, a real ClamAV daemon, and the real Atlas (`c9177d8a-...`) / Lango (`17c1db51-...`) tenants — no mocks, no synthetic unit-test-only claims.

**Environment note:** Docker Desktop's engine stopped mid-session (unrelated to this work) and had to be restarted (`Start-Process "Docker Desktop.exe"`, polled `docker info` until responsive, ~10s). Not a code issue, documented for completeness.

**Confirmed working, live:**
- Real ClamAV integration: the official `clamav/clamav:1.4` image was added to Docker Compose with a health-gated `app` startup (`depends_on: clamav: condition: service_healthy`) — verified the ordering actually held (app did not start until clamav reported healthy), not just that the YAML says so.
- Real malware detection: uploaded the standard EICAR antivirus test string (disguised as a `.docx` to reach the scan step past MIME/magic-byte checks) via a real HTTP multipart POST — rejected `422 INGEST_REJECTED`, asset status set to `infected` in the real DB, **zero** version row ever created, and the download route correctly 404s for it even to its own owner/admin.
- A genuinely clean file (real PNG) uploaded, scanned clean, published, and downloaded back byte-identical with correct `Content-Disposition`/`nosniff`/real-detected-`Content-Type` headers — proving the scanner isn't failing everything indiscriminately.
- Full version/reuse lifecycle: replaced a published asset's file (creates v2, reverts status to `ready` by design so a swapped file never silently goes live without an explicit re-publish); confirmed v1's version row and the usage-link both survive unchanged; confirmed the download route now serves v2's real bytes; confirmed archiving blocks download unconditionally, even for the owner.
- Audience targeting: confirmed a class-section-targeted asset is visible to a real student in that section and invisible to a real student in a different section of the same class; confirmed a `studentVisible: false` (staff-only/answer-key) asset is invisible to a targeted student despite a matching section target, while still visible to the owning teacher/admin; confirmed changing a target immediately de-authorizes a previously-visible asset on the very next request (no caching/staleness).
- Cross-tenant sweep: a Lango-tenant admin was rejected (`404`) on every read/write route against Atlas's real IDs (attachment-type update, asset detail, download, publish, archive, targets-update) and rejected (`422`, asset never created) when attempting to create an asset referencing Atlas's real `attachmentTypeId`.

**Bugs found and fixed during live execution (not caught by planning or unit tests):**
1. **`allowedMimeFamilies` was stored but never enforced.** `AssetService.ingestVersion` checked file size and per-extension magic bytes but never cross-checked the uploaded file's MIME family against the attachment type's configured `allowedMimeFamilies` — an "Images only" type would have silently accepted a Word document. Found while constructing the EICAR test (needed a MIME type with no magic-byte check to reach the scanner) and confirmed missing on inspection. Fixed by adding a `MIME_TO_FAMILY` map and a real family-membership check in `ingestVersion`, before the magic-byte check.
2. **No route existed to change an asset's targets after creation.** `AssetService.setTargets` was only ever called from the create route — there was no way to retarget an already-published asset, which the PRD's own acceptance criterion ("Audience changes take effect immediately even if an old download URL exists") requires to even be testable. Added `PUT /api/content/assets/[id]/targets` (same auth/ownership chain as the other asset routes; teachers blocked from setting `school`/`role`-kind targets, matching the create-route restriction).
3. **Test-environment gap, not a code bug:** no real student password credentials exist for seeded test students (same gap noted in this session's assessment-and-examination remediation). Rather than forging a session (better-auth signs its session cookie; a raw DB-inserted session token doesn't validate), added a minimal `?asStudentId=` admin-preview override to `GET /api/content/assets` — restricted to `school_admin`/`super_admin` — mirroring the exact precedent already established on the homework route (`?studentId=`) from the prior remediation. This is a small, real, useful admin feature (preview what a specific student sees), not a security-weakening shortcut - it requires the caller to already be an authenticated admin.
