## Architecture Overview

This is a remediation, not a greenfield build, within the existing Next.js 15 App Router / TypeScript / Drizzle ORM / PostgreSQL, multi-tenant stack. The addon already has correct schema, migration, and roughly half of its query logic — the fix is: (1) seed the DB-side `report_definitions` table so foreign-key-dependent tables stop failing, (2) bring every route to this codebase's established convention (auth → tenant → addon-entitlement → capability → validation → query → audit → error-handling), (3) replace fabricated adapter data with real Drizzle queries, (4) wire the run engine to route every report key to its real adapter with an honest "not ready" state for the genuinely unbuildable ones, (5) build genuine CSV/XLSX/PDF exports with durable tenant-namespaced storage, (6) build this codebase's first-ever in-process scheduled-task mechanism via Next.js 15's `instrumentation.ts`, and (7) rebuild a real automated test suite for the invariants a prior agent fabricated. Deployed as a single Docker Compose container (`schoolos-app`), same as every other feature in this codebase.

## Tech Stack

- Frontend: Next.js 15 App Router, React, existing UI component library (unchanged — no visual redesign per PRD)
- Backend: Next.js API routes, Drizzle ORM, PostgreSQL
- Auth: existing `requireRequestContext`/`requireTenant`/`requireCapability`/`requireAddon` stack (unchanged, just correctly applied)
- Storage: existing tenant-namespaced local-disk uploads volume (`UPLOADS_DIR`/`/app/uploads`), new usage pattern for server-generated (not user-uploaded) files
- New dependencies: `exceljs` (real XLSX generation), `pdfkit` + `@types/pdfkit` (real PDF generation), `cron-parser` (real cron expression parsing)
- Scheduling: Next.js 15 `instrumentation.ts` `register()` hook + in-process `setInterval` (new pattern for this codebase — no prior precedent existed)
- Hosting: unchanged, existing Docker Compose deployment (`schoolos-app`, `schoolos-db`)

- **section-01, task 01-01:** Confirmed `CORE_REPORT_DEFINITIONS` in `catalog-definitions.ts` already contains exactly 27 entries (4 Student, 4 Fees, 5 Financial, 5 Attendance, 2 HR, 3 Examination, 4 Inventory) — the 4 Platform/Audit reports from the original 31-report plan were never added to this in-memory array at all, so "cutting them from scope" required no code removal, only the documentation decision already recorded. Migration `0062_seed_report_definitions.sql` seeds all 27, verified idempotent (both via a real `docker compose run migrate` second pass and a direct manual re-run of the SQL through psql — both `INSERT ... ON CONFLICT` with 0 errors, row count stays at 27). Live-verified the FK blocker is fixed: a real `report_runs` insert referencing `student.siblings` now succeeds (previously a live 500/FK violation per the audit).
- **section-01, task 01-02:** Corrected per the note already in section-01's file — `report_artifacts` already has the exact columns needed (`filePath`, `fileSizeBytes`, `checksumSha256`, `expiresAt`); no migration was needed. Sections 02 and 05 were updated to reference `report_artifacts` instead of nonexistent `report_runs.artifactExpiresAt`/`artifactDeletedAt` columns.
- **section-10, live verification finding:** the scheduler worker never fired at all - `instrumentation.ts` was placed at the project root, but this project uses the `src/` directory convention (confirmed via `src/middleware.ts`), under which Next.js only looks for `src/instrumentation.ts`. The root-level file was silently never picked up by the build (no compiled instrumentation hook existed anywhere in `.next/` or `server.js` in the running container) - `register()` was simply never called, with no error anywhere to indicate it. Fixed by moving the file to `src/instrumentation.ts`. Found only by checking real container internals after a live in-process interval genuinely failed to fire on schedule - neither `tsc` nor a build-success log would ever catch a file Next.js silently ignores.
- **section-10, live verification finding:** the real PDF export (section-05) failed in the actual Docker container with `ENOENT: /ROOT/node_modules/pdfkit/js/data/Helvetica.afm`. Root cause, found in two layers: (1) `outputFileTracingIncludes` alone was not enough - the `.afm` files were confirmed present on disk at the real `/app/node_modules/pdfkit/js/data/` path, but pdfkit's bundled code was looking for them at a Turbopack-rewritten virtual path (`/ROOT/...`) that doesn't exist at runtime, because Turbopack's server bundling rewrites `__dirname`-based lookups when it bundles a package's code, and pdfkit locates its AFM font files via `__dirname` internally. (2) Fixed by adding `serverExternalPackages: ['pdfkit']`, which tells Next.js to `require()` pdfkit natively instead of bundling/rewriting it, preserving its real filesystem resolution - combined with keeping `outputFileTracingIncludes` so the actual files are still copied into the standalone output. This is exactly the class of bug only a real Docker-built, real-container live test catches - `npx tsc --noEmit` and a local `next dev` run would never surface it, since dev mode doesn't bundle server routes through Turbopack's production path the same way.
- **section-06, task 06-04:** `report_runs` has no column distinguishing a schedule-triggered run from a manually-triggered one, so the completion badge counts any completed run since the user's last visit to the Runs page, not specifically schedule-triggered ones. This is a deliberate simplification to avoid adding a new schema column for a purely cosmetic feature - the badge still honestly reflects "new results are ready," just not scoped to scheduler-only origin.
- **Docker gotcha (repeat of an earlier-session lesson):** The `migrate` service's Docker image is built with `COPY migrations ./migrations` at build time — forgetting to `docker compose build migrate` after adding a new migration file causes `docker compose run migrate` to silently report "success" while doing nothing (the container's stale `/app/migrations` snapshot doesn't include the new file, so every already-applied migration's skip-check short-circuits with zero real work). Caught this immediately via a live row-count check rather than trusting the "MIGRATION SUCCESS" log line alone.
