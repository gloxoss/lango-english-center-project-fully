# Advanced Reporting Addon — Remediation — Product Requirements

> Generated by UltraPlan | 2026-08-06
> This document describes what we're fixing, in plain English.
> For the technical implementation plan, see PLAN.md.

## What We're Building

We're fixing the school's "Advanced Reporting" add-on so it actually works. This is the tool that's supposed to let school staff run reports — like a full list of students, an attendance summary, or a financial statement — and download them as a spreadsheet or PDF. Right now, even though a previous attempt claimed this was finished and working, almost none of it actually functions: running most reports crashes, generated files are fake, and the security checks that are supposed to restrict who sees sensitive information don't run at all. This project makes every report genuinely work, makes the security checks actually enforce, and removes every place where fake sample data was standing in for the real thing.

## The Problem

A previous build of this feature said it was "100% done and verified," but it was not. When we checked it against the real, running app, we found that generating any report crashes with an error, permission checks are silently skipped, and two of the report's headline claims (a balance-sheet calculation and a payroll-privacy rule) turned out to be fake numbers typed directly into the code rather than real calculations. This matters because school staff would be trusting this tool with sensitive information — payroll, financial records, student data — and right now it neither works nor protects that information the way it claims to.

## Who It's For

**School Administrators** (primary): Run any report in the system, including the most sensitive ones like payroll and financial statements. They're the only ones who can turn confidential reports on for a report, or unlock reporting for the whole school.

**Teachers**: Can run everyday reports about their own students and classes — things like attendance and grades — but not payroll or full financial statements.

**Accountants**: Can run the everyday reports everyone gets, plus the fee and financial reports that are their actual job (fee collection, balance sheets, income statements) — but not payroll or student-credential reports, which aren't their job.

**Parents**: Not included in this fix. A parent-facing version (where a parent only sees reports about their own child) is a bigger, different feature — it's deliberately left for later.

## What It Does

### Must Have (this fix)
- Every report in the catalog either runs against real school data, or clearly says "not available yet" — never fake sample numbers pretending to be real.
- Only the right people can run each report, based on how sensitive it is (everyday reports vs. restricted vs. confidential), and that check is actually enforced, not just written down and ignored.
- Downloading a report as a CSV file, a real Excel spreadsheet, or a real PDF all work correctly — currently the "Excel" file isn't really Excel format, and the "PDF" isn't really a PDF.
- A report can be scheduled to run automatically later, and it will actually run — right now, scheduling does nothing.
- Every report run, download, and schedule change is written to the school's activity log, matching how every other sensitive action in this app is already tracked.
- A rebuilt set of automated checks that actually prove the previously-fake claims (like the balance-sheet math) are correct, so a future "it's done" claim can't be false again without being caught immediately.

### Should Have (part of this same fix, lower risk if skipped)
- A safety limit on how much data one report can pull at once, so a very large report can't slow down the whole app.
- Generated report files are saved for a little while so they can be re-downloaded without re-running the report, and old files get cleaned up automatically after a few months.
- A small notification badge showing when a scheduled report has finished running.

### Nice to Have (explicitly out of scope for this fix — see "What It Does NOT Do")
- Reports scoped to a single parent's own child.
- The 4 additional "platform-wide" reports that were originally planned but never built.

## How It Should Feel

Nothing about how the reporting pages *look* needs to change — the pages, menus, and layout already exist and look fine. What needs to feel different is trust: when a staff member clicks "run report," it should reliably either show them real numbers or clearly tell them it's not ready yet — never something in between that looks real but isn't. Reports that aren't ready yet should be visibly greyed out with a "coming soon" label, so it's obvious at a glance what's usable today.

## What It Connects To

This fix doesn't add any new outside connections. It uses the school's own existing database more completely (today, most reports never actually touch it). It reuses the same file-storage system already used for things like student photos and documents, so generated report files are stored consistently with everything else. It adds two small, well-known, free code libraries so Excel and PDF files are genuinely in those formats rather than fake versions pretending to be. Scheduled reports show up inside the app itself — no emails or texts are sent for this fix.

## What It Does NOT Do

- This fix does not add parent access to reports (viewing only their own child's data) — that's a meaningfully different, more complex feature saved for later.
- It does not add the 4 extra "platform-wide" reports from the original plan — those are being formally dropped from scope, not built.
- It does not send reports by email or text message — completed scheduled reports appear inside the app only.
- It does not change who is allowed to turn this feature on for a school in the first place — that switch (already a separate, working system) is left exactly as it is.
- It does not redesign how any of the report pages look — only what happens when you use them.

## How We'll Know It Works

- Every report in the catalog can actually be run by an admin against real school data, and the numbers shown match what's really in the database (checked by hand, not just trusted).
- A teacher, accountant, and admin each see the correct set of reports for their role — nothing hidden that should be visible, nothing visible that should be hidden — checked by actually logging in as each and trying.
- Downloaded CSV, Excel, and PDF files all open correctly in their real programs (Excel, a PDF reader) and contain the right data.
- A scheduled report, once due, actually runs on its own and the result shows up without anyone clicking anything.
- The automated test suite genuinely fails if someone reintroduces fake data or breaks a real business rule (like the balance-sheet math) — proven by intentionally breaking something and watching the test catch it.
- No report can be accessed by someone in a different school, verified the same way every other feature in this app has been tested this session (trying it for real, from another school's account, and confirming it's rejected).

## Business Model

This add-on is already sold to schools as an optional paid feature, separately from the base system — schools have to be specifically granted access to it (the same way other optional add-ons in this app work). This fix does not change that system at all; it only makes the add-on actually work correctly once a school has it turned on. Turning it on for any real school is a separate decision made after this fix is complete and verified, not part of this work itself.

## Risks & Concerns

1. **No existing pattern for "run this automatically later" in this app.** Every other automatic/background behavior in this codebase runs instantly when triggered by a person — there's no existing example of the app doing something on a timer by itself. Building this for the first time carries more risk of subtle bugs than reusing something already proven. We're keeping it as simple as possible (a lightweight timer inside the app itself, checking every few minutes) specifically to reduce that risk.
2. **Two new outside code libraries are being added** (for real Excel and real PDF files). Both are extremely well-established and widely used, but any new outside code is a small trust step that wasn't needed before.
3. **The most sensitive reports (payroll, financial statements, student credentials) are exactly the ones being fixed.** Extra care and extra verification are warranted here, specifically because getting this wrong has real consequences — this is reflected in the plan's emphasis on rebuilding real automated tests, not just spot-checking by hand.
4. **A previous attempt already claimed this was "100% done and verified" while it mostly wasn't.** The main defense against this happening again is the same one used everywhere else in this session: nothing is marked complete without independently trying it against the real, running app and the real database — not just reading the code and trusting it.
