Partie A
Architecture Système & Scoping Académique
A.1 Problématique & Philosophie de Scoping

Dans un établissement scolaire privé, la structure des classes, les matières enseignées et les affectations des professeurs évoluent chaque année. Historiquement, les systèmes ERP rigides imposaient la reconfiguration manuelle de dizaines de classes, de centaines de cours et de milliers d'affectations au début de chaque année scolaire, entraînant un risque élevé d'erreurs humaines et une perte de temps considérable pour la direction pédagogique.

L'architecture Academic Management Enhancement (ADR-001) de SchoolOS résout ce problème en introduisant le concept de Scoping par Session Académique (`sessionYears`). Au lieu de considérer les classes et les sections comme des entités statiques indépendantes du temps, le système sépare la définition structurelle d'une classe (par exemple, 1ère Année Bac - Section A) de son offre concrète pour une année donnée (représentée par la table academicClassOfferings).

Règle d'Or Architectural (ADR-001) : Une offre de classe (Class Offering) réunit un établissement (tenantId), une année académique (sessionYearId), une classe (classId) et une section (sectionId). Toutes les matières (classSubjects) et les affectations de professeurs (classTeachers, subjectTeachers) s'articulent autour de cet identifiant unique offeringId.
A.2 Modèle de Données & Arbre de Dépendances

Pour comprendre le fonctionnement de la copie de session, il faut visualiser l'arbre de dépendances relationnelles au sein de la base de données PostgreSQL. La copie s'effectue en cascade du niveau racine vers les feuilles :

[session_years] (ex: 2025-2026 Source ──► 2026-2027 Cible) │ ▼ [academic_class_offerings] (Offres de Classes : tenant_id + session_year_id + class_id + section_id) │ ├─────────────────────────────────────────┐ ▼ ▼ [class_subjects] [class_teachers] (Matières du Programme par Offre) (Professeurs Principaux de Classe) │ ▼ [subject_teachers] (Professeurs Affectés par Matière et Offre)

Le workflow de copie doit obligatoirement respecter cet ordre d'insertion strict pour garantir l'intégrité référentielle des clés étrangères :

  1. Étape 1 : Offres de Classes (academic_class_offerings) : On duplique les offres actives de la session source vers la session cible. Un mapping dynamique createdOfferingMap : Map<sourceOfferingId, targetOfferingId> est construit en mémoire.
  2. Étape 2 : Programme de Matières (class_subjects) : On duplique chaque matière rattachée à une offre source en la reliant à la nouvelle offre cible via le createdOfferingMap.
  3. Étape 3 : Professeurs Principaux (class_teachers) : On réaffecte les rôles de professeurs principaux aux nouvelles offres cibles.
  4. Étape 4 : Professeurs de Matières (subject_teachers) : On lie les professeurs de matières aux nouveaux couples (targetOfferingId, targetClassSubjectId).
Partie B
Concepts Clés & Moteur de Duplication
B.1 Dry-Run & Mode Aperçu (`preview`)

Avant d'exécuter une écriture définitive en base de données, l'administrateur scolaire a besoin d'une visibilité totale sur l'impact de la copie. L'API POST /api/academics/class-offerings/copy prend un paramètre mode qui accepte deux valeurs : 'preview' ou 'commit'.

En mode Aperçu (`preview`), l'API exécute une simulation complète en lecture seule (sans aucune transaction d'écriture) et retourne un résumé statistique précis :

{ "success": true, "mode": "preview", "summary": { "sourceSessionName": "2025-2026", "targetSessionName": "2026-2027", "sourceOfferingsCount": 4, "offeringsToCreateCount": 4, "offeringsSkippedCount": 0, "classSubjectsToCreateCount": 12, "classTeachersToCreateCount": 4, "subjectTeachersToCreateCount": 12 } }

Ce calcul préventif permet d'afficher des badges informatifs dans l'interface utilisateur, évitant toute surprise avant la confirmation finale.

B.2 Copie Transactionnelle & Idempotence

Lorsque le mode passer à Confirmation (`commit`), la sécurité de l'opération repose sur deux piliers majeurs :

1. Transactions ACID (Drizzle / Postgres)

Toutes les insertions s'exécutent au sein d'un bloc db.transaction(async (tx) => { ... }). Si un incident survient au milieu de la procédure, PostgreSQL annule instantanément (rollback) toutes les modifications. La base reste 100% propre.

2. Clé d'Idempotence (Audit Log)

Pour éviter qu'un double-clic d'un utilisateur sur le bouton "Confirmer" ou un rechargement de page ne duplique l'opération, le client génère un UUID unique (idempotencyKey). L'API vérifie dans audit_logs si ce jeton a déjà été traité. Si oui, elle renvoie une réponse idempotente sans réexécuter la copie.

B.3 Gestion Résiliente des Conflits d'Unicité (Postgres Code 23505 / 409)

Un défi majeur lors de la copie de session survient lorsque la session cible contient déjà partiellement certaines offres ou affectations (par exemple si une classe a été créée manuellement au préalable). Dans une implémentation naïve, une tentative d'insertion d'une clé d'unicité existante déclenche une erreur PostgreSQL code: '23505' (Unique Violation), interrompant brusquement la transaction et renvoyant une erreur 409 Conflict (Un enregistrement identique existe déjà).

Pour garantir un comportement totalement fluide et résilient, le moteur de copie de SchoolOS applique un pattern d'insertion sécurisé en 3 étapes pour chaque entité :

  1. Vérification préalable (Pre-Check SELECT) : Avant d'insérer, le moteur vérifie si l'enregistrement existe déjà dans la session cible.
  2. Bypass des conflits (.onConflictDoNothing()) : Si l'insertion est exécutée, la clause ON CONFLICT DO NOTHING empêche PostgreSQL d'émettre une exception d'unicité.
  3. Récupération des identifiants existants : Si l'enregistrement existait déjà, le moteur récupère son identifiant unique existant pour alimenter correctement les tables filles en cascade.
Résultat : L'opération de copie devient totalement tolérante aux exécutions répétées ou partielles. Les éléments manquants sont créés, tandis que les éléments déjà présents sont préservés et réutilisés sans aucune erreur 409.

C.1 Code Minimal du Modèle Mental (Extrait d'API)

Voici une version simplifiée et pédagogique du cœur de l'API de copie transactionnelle (src/app/api/academics/class-offerings/copy/route.ts) démontrant le mapping dynamique et la résolution des conflits :

// Extrait d'implémentation résiliente dans copy/route.ts const resultSummary = await db.transaction(async (tx) => { const createdOfferingMap = new Map<string, string>(); // sourceOfferingId -> targetOfferingId // 1. Duplication sécurisée des Offres de Classe for (const offToCreate of offeringsToCreate) { const [inserted] = await tx .insert(academicClassOfferings) .values({ tenantId, sessionYearId: targetSessionYearId, classId: offToCreate.classId, sectionId: offToCreate.sectionId, capacity: offToCreate.capacity, status: 'active', }) .onConflictDoNothing() .returning({ id: academicClassOfferings.id }); if (inserted) { createdOfferingMap.set(offToCreate.id, inserted.id); } else { // En cas de présence préalable, on récupère l'offre existante const [existing] = await tx .select({ id: academicClassOfferings.id }) .from(academicClassOfferings) .where(and( eq(academicClassOfferings.tenantId, tenantId), eq(academicClassOfferings.sessionYearId, targetSessionYearId), eq(academicClassOfferings.classId, offToCreate.classId), eq(academicClassOfferings.sectionId, offToCreate.sectionId), )).limit(1); if (existing) { createdOfferingMap.set(offToCreate.id, existing.id); } } } // 2. Duplication sécurisée des Matières par Classe (classSubjects) for (const subj of linkedSubjects) { const targetOfferingId = createdOfferingMap.get(subj.offeringId); if (!targetOfferingId) continue; const [existingSubj] = await tx .select({ id: classSubjects.id }) .from(classSubjects) .where(and( eq(classSubjects.tenantId, tenantId), eq(classSubjects.offeringId, targetOfferingId), eq(classSubjects.subjectId, subj.subjectId), )).limit(1); if (!existingSubj) { await tx.insert(classSubjects).values({ tenantId, classId: subj.classId, subjectId: subj.subjectId, type: subj.type, offeringId: targetOfferingId, }).onConflictDoNothing(); } } });
C.2 Guide d'Utilisation Étape par Étape pour l'Administrateur

Pour exécuter et traiter la copie de session sur l'interface web de SchoolOS :

  1. Accéder à la Page : Naviguez vers /dashboard/academics/session-copy.
  2. Sélectionner la Session Source (Origine) : Choisissez l'année académique active à dupliquer (ex: 2025-2026).
  3. Sélectionner la Session Cible (Destination) : Choisissez l'année académique future (ex: 2026-2027). Note : Si la session cible n'existe pas encore, un bouton d'action directe + Créer Session 2026-2027 vous permet de la créer instantanément sur la page.
  4. Générer l'Aperçu (`Aperçu de la copie`) : Cliquez sur le bouton bleu. L'interface affiche le bilan complet des offres et des matières qui vont être créées.
  5. Confirmer la Copie (`Confirmer la copie`) : Cliquez sur la confirmation. Le message de succès La configuration académique a été copiée avec succès dans la session cible s'affiche.
  6. Consulter et Traiter le Résultat : Vous pouvez désormais consulter et ajuster la nouvelle structure dans les sous-pages dédiées :
    • Offres de Classe (/dashboard/academics/classes) : Ajuster les capacités d'accueil pour la nouvelle année.
    • Matières par Classe (/dashboard/academics/class-subjects) : Modifier les coefficients ou le volume horaire.
    • Attributions Professeurs (/dashboard/academics/class-section-teachers) : Mettre à jour les affectations des enseignants pour 2026-2027.
    • Promotion des Élèves (/dashboard/academics/promotions) : Faire passer les étudiants de 2025-2026 vers les nouvelles offres de 2026-2027.
C.3 Bonnes Pratiques & Guide de Diagnostic
Bonne Pratique : Indépendance des Sessions

Une fois la copie terminée, la nouvelle session est 100% autonome. Toute modification effectuée sur 2026-2027 n'impactera jamais l'historique de 2025-2026.

Diagnostic : Erreur 400 (Bad Request)

Si l'API renvoie 400, vérifiez que la session source et la session cible sélectionnées sont bien différentes. Sélectionner la même session est interdit par la validation Zod.
